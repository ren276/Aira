# Phase 06 Plan 01: Strava Onboarding, OAuth, Daily Ingestion, and Persistence

## Objective

Add mandatory Strava integration at onboarding, ingest all available historical activities then continue incremental daily sync, map activities into Aira metrics inputs, and persist data locally in Room with optional Health Connect write-back support.

## Wave Outline

### Wave 1: Onboarding entry and connection UX

Goals:

- Add a dedicated Strava integration step at the start of onboarding.
- Make Strava connection required before entering permission batching.
- Preserve existing auth and permission onboarding flow correctness.

Planned work:

- Add a new onboarding route/screen for Strava connection before permission batching.
- Extend onboarding step counters and state transitions.
- Store onboarding connection state and reconnect-required state in local preferences.

Success criteria:

- User must connect Strava to proceed to permission onboarding.
- Auth failures produce recoverable retry UX and do not dead-end onboarding.

### Wave 2: OAuth client and secure token lifecycle

Goals:

- Implement robust Strava OAuth auth code flow.
- Persist and refresh credentials safely.
- Handle disconnect/revoke flows cleanly.

Planned work:

- Implement Strava auth endpoints integration and redirect handling.
- Add secure token persistence model (access token, refresh token, expiry, scopes, athlete id).
- Add refresh-on-expiry logic and revoked-token recovery path.
- Add explicit disconnect action clearing local credentials and cursors.

Success criteria:

- Valid token session can be created, restored, refreshed, and revoked.
- Token refresh failure transitions to reconnect-required state without crashing workers.

### Wave 3: Incremental activities ingestion pipeline

Goals:

- Pull full historical activities on first connect, then incremental activities using Strava list endpoint.
- Ensure idempotent sync and safe pagination.
- Protect against partial ingestion corruption.

Planned work:

- Implement activities API client using `after`, `before`, `page`, `per_page`.
- Implement first-run backfill mode that pages through all available history under rate-limit-aware throttling.
- Add local sync cursor storage and page-wise ingestion checkpoints.
- Add idempotency with Strava activity id dedupe.
- Add worker/use case orchestration for app-open sync and daily background sync triggers.

Success criteria:

- Re-running sync does not duplicate already ingested activities.
- Cursor only advances after successful persistence.
- Worker can resume safely after interruption.
- First-run full-history import completes deterministically across multiple paged runs if needed.

### Wave 4: Activity mapping to Aira metrics and persistence

Goals:

- Convert Strava activities into Aira-compatible daily and workout inputs.
- Persist in Room as primary source of truth.
- Optionally mirror into Health Connect behind user control.

Planned work:

- Map activity fields to `WorkoutSession` and supporting metadata.
- Ingest all Strava activity types; guarantee full mapping contract for run/ride/walk/hike and fallback mapping for the rest.
- Normalize units and missing-field behavior (for example no HR on some activities).
- Integrate ingestion output into existing daily computation path through existing Room reads.
- Implement optional Health Connect write-back path guarded by capability and user opt-in.
- Merge duplicate Health Connect/Strava workout candidates with highest-confidence-source-wins policy.

Success criteria:

- New Strava activities are visible through existing workout-based scoring inputs.
- Daily active minutes and related metrics reflect newly ingested sessions.
- Health Connect mirror path can be disabled without affecting Room persistence.

### Wave 5: Rate-limit and fault handling hardening

Goals:

- Make sync resilient to Strava API constraints and transient failures.
- Avoid user-visible instability from external API outages.

Planned work:

- Add structured handling for 401, 403, 429, and 5xx responses.
- Implement backoff/defer policies aligned with WorkManager.
- Parse and surface Strava fault information into developer-safe telemetry and user-safe UI messages.
- Use Strava rate headers (`X-RateLimit-Limit`, `X-RateLimit-Usage`, `X-ReadRateLimit-Limit`, `X-ReadRateLimit-Usage`) to pre-throttle requests.
- Tune request pacing to Strava default limits (200/15min and 2000/day overall; 100/15min and 1000/day non-upload).

Success criteria:

- 429 responses defer sync without data corruption.
- 401/invalid token paths trigger reconnect-required state.
- 5xx/transient errors are retried under bounded policy.

### Wave 6: Verification and rollout gates

Goals:

- Validate onboarding, sync correctness, idempotency, and persistence behavior.
- Lock in regressions with tests and UAT evidence.

Planned work:

- Add unit tests for token lifecycle, cursor logic, dedupe logic, and mapping behavior.
- Add integration tests for onboarding transitions and sync-triggered persistence.
- Add explicit UAT script covering connect, skip, revoke, reconnect, and multi-day sync.

Success criteria:

- All verification gates pass for compile and tests.
- UAT confirms end-to-end flow from onboarding connect to visible daily metrics impact.

## Plan Notes

- Room persistence is mandatory for this phase.
- Health Connect write-back is optional and should be guarded with explicit user consent and capability checks.
- This plan intentionally reuses existing workout and daily score pipelines rather than introducing a parallel scoring path.
- Onboarding entry for Strava is mandatory in this phase as requested.
- Sync cadence includes app-open foreground sync plus daily background sync.

## Verification Gates

Primary gates:

- `./gradlew.bat :app:compileDevDebugKotlin`
- `./gradlew.bat :app:testDevDebugUnitTest`
- `./gradlew.bat :app:compileDevDebugAndroidTestKotlin`

Secondary gates:

- Strava OAuth happy path and revoked-token path tests
- Cursor/idempotency ingestion tests
- Onboarding connect/skip flow tests
- Manual UAT replay for sync visibility in Train/Home metrics

## Outcome

After execution, users can connect Strava during onboarding, Aira ingests activities daily without duplication, and those activities persist locally to influence existing metrics pipelines with stable error handling.
