# Phase 1 Context: Environment & Persistence

**Phase:** 1 — Environment & Persistence
**Captured:** 2026-04-15
**Status:** Ready for planning

## Phase Goal

Establish the foundational Android workspace: project scaffold with flavors, SQLCipher-encrypted Room database, Supabase Auth with Google Sign-In/email/guest, granular permission batching UX, and all baseline security configurations.

## Decisions

### 1. Permission UX Flow
- **Rationale style:** Individual rationale screen per batch (3 screens total: Core → Body → Advanced). Each screen clearly lists the permissions in that batch with plain-English explanations before launching the system dialog.
- **Core batch denial handling:** Hard block — show a full-screen "Aira needs these permissions" screen with a loop. User can tap "Use limited mode" as the only escape hatch.
- **Limited mode re-prompt:** Permission prompt reappears on every cold launch (NOT permanently suppressed). No DataStore flag is set — the prompt loops until the user grants or explicitly chooses limited mode each time.
- **Degraded mode:** If denied, app enters limited mode. Scores that rely on missing data show "—" with a contextual tap-to-grant chip on each affected card.

### 2. SQLCipher Bootstrap Sequence
- **Key timing:** AES-256 key is generated by Android Keystore on **first cold start**, before any UI is shown. Room opens immediately with that key — no biometric gate on the DB itself.
- **Biometric App Lock:** Implemented as a **separate, optional UI layer**. It gates the app UI (e.g., via a lock screen Composable on resume), not the database. Off by default.
- **Where to enable:** Settings → Security → App Lock. Falls back to device PIN/pattern if biometrics not enrolled.
- **No hard dependency:** App is fully functional without biometrics enabled.

### 3. Supabase Session Strategy
- **Phase 1 architecture:** Room is the **single source of truth** for all data. ViewModels observe Room `Flow<>` exclusively — no Supabase reads in the UI layer.
- **Supabase role (Phase 1):** Auth only + async background sync. Scores, corrections, and baselines are pushed to Supabase via WorkManager after being computed locally. No real-time subscriptions.
- **Guest mode:** Supabase is **never initialised** in guest mode. 100% local — no network calls from the data layer.
- **Guest → real account migration:** On account creation, existing Room data is tagged with the new `user_id` and synced in a one-time background job.
- **Phase 4 evolution:** Real-time Supabase subscriptions (cross-device sync) are planned for Phase 4 when the UI layer is mature.

### 4. Package & Build Config
- **Application ID:** `com.aira.health` (Play Store compliant, reverse-domain format).
- **Product flavors (set up in Phase 1):**
  - `debug` — extra logging enabled, FLAG_SECURE **disabled** (dev screenshots work), points to local/staging Supabase.
  - `staging` — FLAG_SECURE enabled, points to **Supabase staging project** (separate project from production).
  - `release` — FLAG_SECURE enabled, points to **Supabase production project**, R8/ProGuard minification on.
- **Build types:** Standard `debug` + `release` build types combined with the above flavors.
- **Rationale:** Setting up flavors now is far cheaper than retrofitting later. Staging environment needed once Supabase sync is live in Phase 3+.

## Success Criteria (from ROADMAP.md)

1. App successfully requests permission batches with individual rationale screens; Core denial loops with "Use limited mode" escape.
2. Users can create accounts via Supabase (Google Sign-In, email, or anonymous guest). Guest mode makes zero Supabase network calls.
3. Local Room database spins up using SQLCipher with an Android Keystore-backed key. Biometric App Lock is available but optional in Settings.
4. `debug` / `staging` / `release` product flavors are configured, each pointing to the correct Supabase environment.
