# Phase 05 Plan 01: Runtime Data Wiring & UI Alignment

## Objective

Rewire the current app so every existing UI surface reflects real local data, explicit empty states, and semantically correct navigation behavior.

This phase is about alignment, not new features. The goal is to make the current app honest and consistent end-to-end: the right screen, the right data, the right fallback, and the right state on every path.

## Wave Outline

### Wave 1: Navigation, entry, and route contract cleanup

Goals:

- Keep the app entry flow stable while the shell wiring changes.
- Remove route semantics drift between visible tabs and actual destinations.
- Make deep links and top-level tabs resolve to real destinations only.

Planned work:

- Align `AiraRoutes` with the visible IA and decide which aliases are temporary migration glue.
- Keep `AiraNavHost` and `AiraBottomNav` consistent with the final tab model.
- Verify `AppEntryRoute` still gates onboarding correctly before the shell.
- Make `DeepLinkRouter` fallback behavior deterministic and safe.

Success criteria:

- Top-level navigation matches the current visible IA.
- Unknown or malformed deep links fall back safely.
- Onboarding still gates the shell correctly.

### Wave 2: Home and detail surface alignment

Goals:

- Make the primary dashboard and core detail routes reflect live state with correct semantics.
- Surface freshness and confidence where the contract already expects it.
- Remove any mismatch between metric names, route targets, and explanation behavior.

Planned work:

- Reconcile `HomeViewModel` and `HomeDashboardScreen` so the dashboard shows the right data and state cues.
- Ensure `MetricDetailRoute` dispatches to the correct metric screen.
- Keep explanation-sheet behavior trigger-driven, not always-on.
- Keep Body/Coach aligned to their supporting state sources instead of implying a stronger data product than exists.

Success criteria:

- Home shows live data with visible freshness/confidence context.
- Metric detail routes are semantically correct.
- Explanation surfaces appear only from explicit user action.

### Wave 3: Train and Nutrition wiring

Goals:

- Make quick-add and edit flows honest, resilient, and fully persisted.
- Keep scanner behavior explicit if unavailable.
- Ensure the history lists reflect what is actually in Room.

Planned work:

- Reconcile `TrainViewModel`, `TrainEditViewModel`, `TrainScreen`, and `TrainEditScreen` state and edit behavior.
- Reconcile `NutritionViewModel`, `NutritionEditViewModel`, `NutritionScreen`, and `NutritionEditScreen` state and edit behavior.
- Keep scanner draft handling explicit and non-silent.
- Verify insert/update/delete round-trips update the visible history immediately.

Success criteria:

- Train and Nutrition flows save, edit, and delete correctly.
- Lists reflect Room-backed state immediately after mutation.
- Scanner fallback is explicit if camera-backed scanning is not ready.

### Wave 4: Supplementary and settings runtime state

Goals:

- Bind secondary surfaces to local state or explicit unavailable messaging.
- Remove seeded or static runtime copy from the surfaces that currently look finished but are not data-backed enough.
- Make settings and account reflect actual runtime status.

Planned work:

- Reconcile `InsightsPredictionsViewModel` and `DataCorrectionsViewModel` with local data sources.
- Keep `WhatIfViewModel` in explicit insufficient-data mode instead of implying fabricated baseline values.
- Keep `WeeklyReportViewModel` aligned with recent local metrics and visible trend state.
- Reconcile `SettingsViewModel`, `SettingsScreen`, and `AccountScreen` with actual account, sync, and local-model state.
- Keep Data Confidence as a real route/screen and not only a small badge concept.

Success criteria:

- Supplementary and settings surfaces are state-driven.
- No screen implies fabricated values when data is missing.
- Account and confidence surfaces are visible, reachable, and truthful.

### Wave 5: Global verification and closure

Goals:

- Prove the rewired UI still compiles and the core test harness remains valid.
- Enforce the no-runtime-mock-data contract across the touched presentation surface.
- Capture UAT evidence for the aligned app shell.

Planned work:

- Update or add tests for route contracts, state contracts, and empty-state behavior.
- Keep the global literal scan green for production presentation code.
- Replay the existing UAT checklist against the new wiring.
- Record any residual risks as deferred work instead of hiding them in the UI.

Success criteria:

- Compile, unit tests, and androidTest compile remain green.
- No-runtime-mock-data checks are automated.
- UAT evidence matches the new wiring behavior.

## Plan Notes

- This phase should be executed after Phase 04.1, not instead of it.
- Route compatibility is allowed during migration, but the visible IA must end in a clean state.
- Empty or unavailable UI is acceptable when it is explicit and honest.
- The phase should prefer stable runtime behavior over adding new visual complexity.

## Verification Gates

Primary gates:

- `./gradlew.bat :app:compileDevDebugKotlin`
- `./gradlew.bat :app:testDevDebugUnitTest`
- `./gradlew.bat :app:compileDevDebugAndroidTestKotlin`
- Global literal scan for production presentation files

Secondary gates:

- Targeted route tests
- Home/detail state tests
- Train/Nutrition mutation tests
- Supplementary and settings state tests

## Outcome

When this phase is executed, the current UI should feel like one coherent system again: the same data model, the same navigation model, and the same fallback rules across the whole app.
